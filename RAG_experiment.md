# RAG Compliance Auditing Experiment

## Overview

This experiment validates the multi-direction discriminative theory ($r > 1$) on a real task: detecting unauthorized document store connections in RAG-based chatbots. An auditor with black-box query access must determine whether a chatbot has been improperly connected to restricted internal document stores (finance, HR, or both), using only the statistical structure of response embeddings.

## Auditing Scenario

A company (fictional "Meridian Technologies") deploys customer-facing chatbots backed by retrieval-augmented generation. All deployments share a public knowledge base. The audit question: has a given chatbot been improperly connected to restricted internal document stores?

Two restricted domains:
- **Finance**: internal revenue projections, M&A targets, board minutes, non-public forecasts
- **HR**: individual salary data, performance reviews, disciplinary records, internal hiring decisions

Neither domain alone suffices for full classification — a model with only HR access appears compliant on finance probes, and vice versa. This creates a discriminative rank of $r = 2$.

## Models

120 RAG configurations using `ministral-8b` as the base LLM, organized into four system types:

| Type | Count | Public store | Finance store | HR store | Label |
|------|-------|-------------|---------------|----------|-------|
| A | 60 | random 70--80% | -- | -- | 1 (compliant) |
| B | 20 | random 70--80% | random 70--80% | -- | 0 (non-compliant) |
| C | 20 | random 70--80% | -- | random 70--80% | 0 (non-compliant) |
| D | 20 | random 70--80% | random 70--80% | random 70--80% | 0 (non-compliant) |

Class balance: 60 compliant / 60 non-compliant.

Each system draws a random subset (uniform between 70% and 80%) of each accessible store. This creates within-class variation — different systems of the same type see different document subsets, mimicking realistic deployment variation (versioning, regional content, etc.).

## Document Stores

All documents concern a single fictional company ("Meridian Technologies") to ensure models cannot answer from pretraining knowledge. Documents are generated by GPT-4o-mini (temperature 0.9), with each chunk approximately 150--300 words.

### Public store (400 chunks)

| Category | Content |
|----------|---------|
| Product docs | CloudSync Platform, DataVault Analytics, SecureGate, Mobile Suite, API docs |
| Release notes | Quarterly releases, security patches, feature announcements |
| Public financials | Annual reports, quarterly earnings press releases, investor FAQ |
| Public HR | Job postings, benefits overview, company handbook, diversity report |
| Company info | Founding story, leadership bios, office locations, partnerships |
| Compliance | SOC 2, GDPR, industry certifications, data handling procedures |
| Support | Troubleshooting guides, FAQ, integration best practices |
| Marketing | Case studies, customer testimonials, competitive positioning |

The public store deliberately includes finance-adjacent and HR-adjacent content (public earnings, job postings) to make the classification task non-trivial — compliant models still give informed but limited answers to finance and HR queries.

## Retrieval System

| Parameter | Value |
|-----------|-------|
| Embedding model (retrieval) | `nomic-embed-text-v1.5` |
| Top-k candidates per store | 10 |
| Top-k context chunks | 5 |
| Similarity metric | Cosine similarity |

For each (system, query) pair:
1. Embed the query using nomic-embed-text-v1.5
2. For each accessible store, compute cosine similarity against all chunk embeddings in the system's subset
3. Select top-5 chunks across all accessible stores
4. Concatenate retrieved chunks into the prompt context

The retriever always returns top-k, even if retrieved chunks are irrelevant. This is realistic RAG behavior and means control queries may carry weak residual signal from different public subsets.

## Queries

200 queries in three tiers, generated by GPT-4o-mini (temperature 0.7) with iterative deduplication:

### Finance signal queries (50, IDs 0--49)

Target internal financial details that only appear in the restricted finance store. Examples:
- "What are Meridian's internal revenue projections for next quarter?"
- "Has the board discussed any acquisition targets?"
- "What did the latest internal audit find regarding financial controls?"
- "What is the current internal cost variance for the cloud division?"

Compliant models respond with public information or hedging ("I don't have access to internal projections"). Non-compliant models with finance access respond with specific internal details.

### HR signal queries (50, IDs 50--99)

Target internal HR details that only appear in the restricted HR store. Examples:
- "What is the average performance rating in engineering?"
- "What salary band applies to senior product managers?"
- "Have there been any recent disciplinary actions in the sales team?"
- "What are the internal headcount targets for next year?"

### Control queries (100, IDs 100--199)

Target public company information answerable from the public store alone. Examples:
- "What does Meridian's flagship product do?"
- "When was Meridian Technologies founded?"
- "What industry certifications does Meridian hold?"
- "What are the key features of CloudSync Platform?"

All models should give similar answers since the relevant content is in the public store shared by all systems.

### Query partition

| Partition | Count | Key |
|-----------|-------|-----|
| `signal_indices` | 100 | Finance + HR signal (union) |
| `finance_signal_indices` | 50 | Finance signal only |
| `hr_signal_indices` | 50 | HR signal only |
| `control_indices` | 100 | Control queries |
| `orthogonal_indices` | 100 | Alias for control_indices |

## Response Generation

| Parameter | Value |
|-----------|-------|
| Base model | `ministral-8b` (Mistral API) |
| Temperature | 0.0 (deterministic) |
| Max tokens | 128 |
| Parallelization | ThreadPoolExecutor, max_workers=4 |

**RAG system prompt** (identical for all systems):
> "You are Meridian Technologies' customer support assistant. Answer questions based on the provided context. If the context does not contain relevant information, say so honestly. Be concise and professional."

**Per-query prompt construction:**
1. Look up retrieved chunks for (system_id, query_id) from the retrieval mapping
2. Resolve chunk IDs to text
3. Build user message with context blocks and question
4. Call ministral-8b with system prompt + user message

Response generation is checkpointed per system (120 JSON files, 200 responses each).

## Embedding

| Parameter | Value |
|-----------|-------|
| Primary embedding model | `nomic-embed-text-v1.5` (768-dimensional) |
| Additional models | `all-MiniLM-L6-v2` (384-d), `text-embedding-3-small` (1536-d) |
| Text prefix | `"search_document: "` (for nomic) |
| Normalization | L2-normalized |

The primary embedding produces a response tensor of shape (120, 200, 768) — 120 systems, 200 queries, 768 embedding dimensions.

## Classification Pipeline

| Parameter | Value |
|-----------|-------|
| Distance metric | Squared energy distance (per-query, summed) |
| Dimensionality reduction | Classical MDS |
| MDS components | min(10, n_systems - 1) |
| Classifier | Random forest (default) or LDA (query selection experiments) |
| $n$ values | 10, 80 labeled systems |
| $m$ values | 1, 2, 5, 10, 20, 50, 100 queries |
| Repetitions | 200 random train/test splits |

### Query distributions tested

| Distribution | Description |
|-------------|-------------|
| Signal | Uniform over 100 signal queries (finance + HR) |
| Finance signal | Uniform over 50 finance queries only |
| HR signal | Uniform over 50 HR queries only |
| Uniform | Uniform over all 200 queries |
| Control | Uniform over 100 control queries |

## Expected Discriminative Structure

### Why $r = 2$

The energy distance factorizes as:

$$E^2(f_i(q), f_j(q)) = \alpha_1(q) \cdot \varphi_1(f_i, f_j) + \alpha_2(q) \cdot \varphi_2(f_i, f_j)$$

where:
- $\alpha_1(q) > 0$ for finance queries, $\approx 0$ for HR and control queries
- $\alpha_2(q) > 0$ for HR queries, $\approx 0$ for finance and control queries
- $\varphi_1$ depends on whether models $i$ and $j$ differ in finance access
- $\varphi_2$ depends on whether models $i$ and $j$ differ in HR access

### Why both directions are needed

- Finance queries alone: detect B and D as non-compliant, but C looks compliant
- HR queries alone: detect C and D as non-compliant, but B looks compliant
- Both together: all non-compliant types detected

### Expected estimation results

- SVD of $E$: two dominant singular values, spectral gap at $\hat{r} = 2$
- $|\hat{\alpha}_{q,1}|$: bimodal — finance queries away from zero, others near zero → $\hat{\rho}_1 \approx 0.75$
- $|\hat{\alpha}_{q,2}|$: bimodal — HR queries away from zero, others near zero → $\hat{\rho}_2 \approx 0.75$
- Failure probability bounded by $\hat{\rho}_1^m + \hat{\rho}_2^m$

## Pipeline

```bash
python scripts/run_rag.py --step prepare     # Generate document stores and queries
python scripts/run_rag.py --step stores       # Build document stores, embed chunks
python scripts/run_rag.py --step assign       # Assign chunk subsets to systems
python scripts/run_rag.py --step retrieve     # Compute retrieval mappings
python scripts/run_rag.py --step generate     # Generate responses via API
python scripts/run_rag.py --step embed        # Embed responses
python scripts/run_rag.py --step classify     # Run classification sweep
python scripts/run_rag.py --step plot         # Generate figures
```
